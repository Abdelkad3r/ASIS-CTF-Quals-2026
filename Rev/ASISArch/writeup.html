ASIS CTF Quals 2026 · Rev

ASIS Arch

A 2.5 KB VM whose instructions are encrypted with the address they sit at — so the same four bytes are a different instruction everywhere.

custom ISA 26 opcodes 16-bit no solver needed solved
Flag 
ASIS{M1ddL3_3nd14n_N1bbL35_M4k3_Q3MU_D122y!}

The whole challenge in one specimen

These four bytes are the first instruction in the ROM. Here is what they decode to at other addresses:

@0x0000c3 3a 7c 4fli r6, 0x7c60
@0x0048c3 3a 7c 4fstb [r5+0x1298], r6
@0x0058c3 3a 7c 4fout r6
@0x00b4c3 3a 7c 4fhalt
@0x010cc3 3a 7c 4fxori r3, 0xffd0
@0x1000c3 3a 7c 4fillegal instruction

Only 1664 of the 16384 aligned addresses decode them to anything legal at all. Every byte of the ROM is welded to its address, which is why a linear sweep produces convincing nonsense and never resynchronises.

01

Recon — the emulator is not QEMU

Real QEMU is measured in megabytes. This is 14 KB, stripped, and the section table gives the game away before a single instruction is read:

SectionSizeWhat it is
.text0x9f5the entire CPU, 2549 bytes
.rodata0x260decode tables and strings
.data.rel.ro0x800256 × 8 — an opcode dispatch table

A 2 KB array of function pointers indexed by a byte is the shape of an interpreter dispatch. Count the table before reading the handlers: it is the instruction set. The strings agree — illegal instruction, PC out of bounds, guest cycle limit exceeded, ROM checksum mismatch.

Behaviour 
$ echo 'ASIS{aaaa}' | ./qemu-asisarch -M asisboard -kernel challenge.rom -nographic
=== ASISARCH Secure Enclave v2.0 ===
Enter flag:
[-] Access Denied. Invalid flag.
02

The ROM container

A 32-byte header is validated before the body is copied to guest address 0:

+0x00  "AARQ"       magic
+0x04  02           version, must be 2
+0x08  byte lo      entry PC, low half  (scrambled)
+0x09  byte hi      entry PC, high half (scrambled)
+0x0c  uint32       checksum over the body
+0x20  image        body, at most 0x10000 bytes

The entry point is not stored directly. It is assembled by swapping the nibbles of each header byte and rotating the result — the same scramble that decodes every instruction immediate, and the thing the flag calls middle-endian nibbles:

entry = rol16((rol8(hdr[9], 4) << 8) | rol8(hdr[8], 4), 5)   # = 0x0000

The checksum is a 16-bit rolling XOR seeded with 0x31415926. Worth reimplementing even though it is not in the way — without it you cannot rebuild a patched ROM.

03

Machine state

The whole machine is one flat allocation, so the layout reads straight off the offsets used in .text:

0x00000 .. 0x0ffff   RAM, 64 KiB
0x10000 .. 0x1000f   r0 .. r7, 16-bit each
0x10010              SP, initialised to 0xfff0
0x10012              PC
0x10018              cycle counter, aborts above 10_000_000

Sixteen-bit registers, byte-addressed little-endian memory, and no flags register — conditional branches test a register directly.

04

The fetch stage

This is the challenge. Before anything is decoded, the fetch stage derives a keystream from the program counter itself, and every field of the instruction is unmasked with it:

Keystream raw = ((PC ^ 0x9e37) * 0x1039 + 0x79b9) & 0xffff
sel = (raw >> 14) & 3   // one of four byte orders
k   = rol16(raw, 5)
Permute b0..b3 = the four fetched bytes, reordered by sel
sel 0: [0,1,2,3]   sel 1: [2,0,3,1]   sel 2: [3,2,1,0]   sel 3: [1,3,0,2]
Opcode op = rol8((0x5d * PC ^ k ^ b2) & 0xff, (k >> 5) & 7) ^ 0x6d
Register x  = (7 * PC ^ (k >> 2) ^ b0) & 0xff
rd = ((5 * (((5 * x) ^ 3) & 7)) ^ 3) & 7
Immediate imm = rol16((rol8((b3 ^ (k >> 8)) & 0xff, 4) << 8)
           | rol8((b1 ^ k) & 0xff, 4), 5)

The second register operand is not in the instruction at all. It is packed into the low three bits of the immediate, through the same permutation, leaving thirteen bits as an address displacement:

rs   = ((5 * (imm & 7)) ^ 3) & 7
disp = imm >> 3
05

Recovering the opcode map without guessing

The dispatch table is zero-filled on disk — it is a table of pointers in a position-independent executable, populated at load time. The opcode numbers are therefore sitting in the relocation table, and can be read out statically:

for reloc in .rela.dyn:
    if reloc.type == R_X86_64_RELATIVE and reloc.offset in dispatch_table:
        opcode = (reloc.offset - table_base) // 8
        handler = reloc.addend        # 26 live, 230 null -> illegal

Why this matters

No debugger, no execution, no guessing about which entries are real. The same pass lifts the S-box and the byte-permutation table out of .rodata, so the only human input left is naming the 26 handler addresses.

06

The instruction set

Arithmetic is written with the carry-free identity x + y == (x ^ y) + 2*(x & y), so neither add nor sub looks like arithmetic at a glance. And sbox is a substitution instruction with no equivalent on any real CPU — the first hint that the ROM is doing block-cipher work.

07

Build an emulator, then prove it right

A reimplementation that merely produces the same text has only exercised the I/O path. Matching the cycle count on both the accepting and the rejecting run exercises every instruction the ROM actually uses:

$ echo 'ASIS{aaaaaaaa}' | python3 asisarch.py
=== ASISARCH Secure Enclave v2.0 ===
Enter flag:
[-] Access Denied. Invalid flag.
[614 cycles]   # byte-identical to the reference binary
08

Disassembling the ROM

Linear sweep is useless, so the disassembler is recursive descent: start at the header's entry PC and follow jmp / jz / jnz / call, stopping at ret and halt. That reaches 7960 instructions — essentially the whole image, with nothing hidden behind computed jumps.

Entry point 
0000:  li r6, 0x7c60      ; banner
0004:  call 0x7c04        ; puts
0008:  li r6, 0x7c86      ; "Enter flag: "
000c:  call 0x7c04
0010:  li r6, 0xc000      ; input buffer
0014:  call 0x7c1c        ; readline -> length in r3
0018:  li r1, 0x002c
001c:  sub r1, r3
0020:  jnz r1, 0x7bf8     ; length != 44 -> reject

The flag is exactly 44 bytes, buffered at 0xc000 — 22 sixteen-bit words.

09

The verification routine

Between the length check and the comparison sits one enormous basic block, 0x0024 to 0x7873, fully unrolled, with no branches at all. Lifting it shows 660 stores to the buffer in three repeating shapes, 220 each — ten rounds of three passes over 22 words:

PassOperation
Substitutew[i] = S16(w[i]) ^ K[round][i]
Diffuse forwardw[i] = w[i] + w[i-1 mod 22] + 0x5a5a
Diffuse backwardw[i] ^= σ(w[i+1]) ^ rol(σ(w[i+2]), r)

with σ(x) = x ^ rol(x,5) ^ rol(x,11), 220 distinct round constants, and a rotation r that increases every round. One pass propagates changes up the buffer and the other propagates them down, so after two rounds every output word depends on every input byte. Guessing the flag piecewise is hopeless.

The comparison then repeats 22 times:

7b20:  li r6, 0xc022        ; a transformed word
7b24:  ldw r3, [r6+0x0]
7b28:  li r1, 0x7cdb        ; constant table
7b2c:  addi r1, 0x0058      ; ... at a shuffled offset
7b30:  ldw r4, [r1+0x0]
7b34:  addi r1, 0x0002
7b38:  ldw r7, [r1+0x0]
7b3c:  xor r4, r7           ; expected = tbl[off] ^ tbl[off+2]
7b40:  xor r3, r4
7b44:  add r5, r3           ; accumulate the difference

No expected word is stored in the clear — each is the XOR of two entries of a 176-byte table, read at offsets that hop around it. Differences are accumulated rather than compared one at a time, so there is no early exit to time and no per-word oracle.

10

Inverting the transform

The winning observation is that the transform has no branches, so its sequence of buffer updates is the same whatever the input is. It can be lifted once, symbolically, by walking the block with an expression per register instead of a value. Buffer loads produce the symbol B[i]; each store emits a step and resets that symbol, so every step is written against the current buffer rather than the original input:

elif name == "ldw":
    sym[rd] = ("B", (a - BUF) // 2) if in_buffer(a) else ("C", word_at(a))
elif name == "stw":
    steps.append(((a - BUF) // 2, sym[rd]))

The result is 660 steps of the form buf[i] <- f(buf[i], other words, constants) with f built only from xor, add, rotate and S-box. Two properties make them trivially invertible:

  • every step mentions its own target exactly once — asserted by the solver — so that occurrence can be isolated by peeling operations from the outside in;
  • the other words a step reads are not modified by that step, so when replaying backwards their post-values are also their pre-values.

Undo xor with xor, add with subtraction, rotate with the opposite rotate, S-box with the inverse permutation. Start from the expected words, run the list backwards, and the input falls out:

$ python3 solve.py
[+] lifted 660 elementary buffer updates
[+] expected words: 544c 15a0 eb44 09d6 b6ab 496e fd0a 3806 f1df 0913 ffd8 ...
[+] flag: ASIS{M1ddL3_3nd14n_N1bbL35_M4k3_Q3MU_D122y!}
[+] emulator says: ACCEPTED (8906 cycles)

No brute force, no SMT solver. The size of the search space never enters into it.

—

Takeaways

  • Size is the first tell. A 2.5 KB .text beside a 2 KB pointer table is an interpreter, and that table is the instruction set. Count it before reading a single handler.
  • Recover tables from relocations, not from a debugger. In a PIE, a table of function pointers lives in .rela.dyn. Parsing it yields the opcode map with nothing executed and nothing guessed.
  • Validate a reimplemented VM on cycle counts. Matching output only proves the I/O path; matching cycles on both paths exercises every instruction the ROM uses.
  • Branch-free obfuscation defeats itself. Unrolling hides the structure from a reader, but it also removes every input-dependent decision — which is exactly what lets the operation sequence be lifted once and inverted in closed form. A single data-dependent branch in that block would have forced a solver.
