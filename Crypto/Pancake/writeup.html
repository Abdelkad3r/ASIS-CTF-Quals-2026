One stack, one keystream.

A "state-of-the-art" AEAD whose fluffy KDF layers all collapse: a truncated-AES collision makes two different nonces derive the same GCM key + IV. One message is known zeros — so its ciphertext is the flag's keystream.

TL;DRTwo bugs, stacked

  1. 32-bit seed leak. k1 = SHA256("K1-SEED" ‖ be32(seed)) but the public hint = SHA256("K1-SEED-HINT" ‖ be32(seed)) is an oracle for the 32-bit seed. Brute 2³² → seed = 0x22c4d3ef → k1.
  2. Truncated-collision KDF ⇒ keystream reuse. The GCM (key, iv) depend only on n1 and j = upper96(AES_k1(n2‖0)). Generation finds alt ≠ n2 with the same top-96 output and encrypts all-zero data under (n1, alt). Same j ⇒ same state ⇒ same (ek, iv) ⇒ same keystream. Zeros in ⇒ ciphertext is the keystream.

flag = y.ciphertext ⊕ sample.ciphertext. The secret k2 is never needed.

01The construction

Public JSON gives d=32 (dropped bits), a (hint), n=[n1,n2], the associated data, m (128 zero bytes), y (flag AEAD blob) and z (a "sealed ticket").

def seed_to_k1(seed):   return sha256(b"K1-SEED"      + seed.to_bytes(4,"big")).digest()
def seed_to_hint(seed): return sha256(b"K1-SEED-HINT" + seed.to_bytes(4,"big")).hexdigest()
def extract_upper(x):   return int.from_bytes(x,"big") >> 32            # top 96 bits

def diffuse_state(k, n1, n2):
    e  = AES.new(k, AES.MODE_ECB)
    j  = extract_upper(e.encrypt(format_block(n2, 0)))                # depends on n2 only via top-96
    w1 = n1 ^ j;  w2 = n1 ^ gf_double(j)
    r1 = extract_upper(e.encrypt(format_block(w1, 0x18)))
    r2 = extract_upper(e.encrypt(format_block(w2, 0x28)))
    return j, w1, w2, r1, r2

def derive_keys(k2, n1, state):                                       # ek=GCM key, iv, ck
    z = shake_256(b"KDF-STATE-v1" + k2 + n1 + j + w1 + w2 + r1 + r2).digest(80)
    return z[:16], z[16:28], z[28:44]

02Bug #1 — a 256-bit key with 32 bits of entropy

k1 is a full AES-256 key, but it is derived from a 32-bit seed, and the published hint is a straight SHA-256 of that seed. Iterate seed ∈ [0, 2³²), hash, compare — a threaded C program finds it in seconds:

$ ./seedbrute 9b23e5ef…13cf
SEED:22c4d3ef        # k1 = SHA256("K1-SEED" ‖ 22c4d3ef)

03Bug #2 — a truncated collision fuses two derivations

find_collision(k1, n2) looks for alt with target = upper96(AES_k1(n2‖0)):

base = target << 32
for sep in range(1 << 32):
    x = AES_k1.decrypt(base | sep)          # 128-bit block
    if (x & 0xffffffff) == 0:               # low 32 bits zero  =>  x = y‖0
        y = x >> 32
        if y != n2: return y                 # a different nonce, same top-96 output

That is a collision in the 32-bit-truncated AES permutation. The server then encrypts the all-zero KNOWN_PLAINTEXT under (n1, alt) and hides that blob in the ticket. Trace both derivations:

the fatal step

Identical (ek, iv) under AES-GCM (a CTR mode) ⇒ identical keystream, regardless of the fresh secret k2. The sample's plaintext is zeros, so its ciphertext is exactly that keystream.

04Recovering the keystream from the sealed ticket

The sample ciphertext lives only inside z, itself AES-GCM with key = SHA256("SEALED-TICKET-KEY" ‖ k1 ‖ n1 ‖ alt)[:16] and a derived nonce. We know k1 and n1; we recompute alt with the same 2³² scan (printing every collision and letting the GCM tag pick the right one). It decrypts cleanly:

alt = 0xa5720dc7719f529e8e9cb565        # record n = [n1, alt] — the reuse, confirmed

The recovered record["x"]["c"] is the reused keystream; XOR with the flag ciphertext:

05Lessons

  • A key is only as strong as its seed. AES-256 from 32 bits has 32-bit security — and a public hash of the seed removes even that.
  • Truncating a PRP manufactures collisions. Dropping 32 bits turns AES into a 96→96 map where distinct nonces readily share an output — here, the same GCM key + IV.
  • Keystream reuse breaks GCM completely. With one colliding message a known all-zero plaintext, its ciphertext is the raw keystream; XOR reveals the other.
  • Fresh randomness you then ignore isn't fresh. The KDF mixes in a random k2, but every other input collided, so k2 bought no security at all.
