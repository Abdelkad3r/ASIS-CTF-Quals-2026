01

Identify the encoding

The flavour text is the hint. Vintage LED displays means seven-segment readouts — a bench multimeter, a clock radio. Only kind human eyes can still decode means the art is hostile to OCR but trivial for a person: no file, no cipher, no steganography. What you see is what you decode.

Three rows per block confirms it. A seven-segment glyph needs exactly three text rows, and the seven segments carry their conventional names:

Segment anatomy 
 _     <- a          top
|_|    <- f g b      upper verticals + middle bar
|_|    <- e d c      lower verticals + bottom bar

Three glyphs in the art are not producible on a real seven-segment display: a diagonal \ for r, a diagonal / for w, and a _|_ crossbar for t. Those are the author's concession to human eyes.

02

Build the font from the art itself

Rather than importing a seven-segment table, derive it from the five blocks. Sixteen glyphs appear. Four are leetspeak substitutions; the rest are literal letters.

Alphabet 
 _           _     _                 _     _
|_    |_|   |_|    _|   | |   |     |     |_
|       |   |\     _|   |/|   |_    |_     _|
 f    4=a    r    3=e    w     l     c     s

             _           _    _|_    _
|     |_|   | |   | |   | |    |    |_|   |
|     | |   |_|   |_|   | |    |      |   .
1=i    h    0=o    u     n     t    9=g    !

Two properties of this alphabet decide the whole challenge:

  • Only three pairs are ambiguous. 4/9, l/c and u/0 differ solely in the top segment. Every other glyph is fully determined by its two lower rows.
  • The font is proportionally spaced. 1 is a single column wide, t spans all three columns of the top row, everything else fills a 3×3 cell. There is no fixed pitch to slice on.
03

Index by column, not by eye

Counting spaces by hand is how this challenge is lost. Dump the ink positions instead. For block 1:

top row  '_' at columns : [5, 13, 17, 25]
row 1 ink at columns   : 4| 5_ 8| 9_ 10| 12| 13_ 14| 17_ 18| 20| 22| 25_ 26| 28| 31|
row 2 ink at columns   : 4| 10| 12| 13\ 17_ 18| 20| 21/ 22| 25_ 26| 28| 29_ 31| 32_

Cells begin at columns 4, 8, 12, 16, 20, 24, 28 — then 31. The pitch of four breaks at the end, because the two trailing l glyphs are packed tighter. That is the first sign that any decoder assuming a fixed pitch will drift off the grid.

04

First pass — blocks 1, 3 and 5

With cells located, three of the five blocks decode straight off:

s stays a letter rather than becoming 5 — the two are drawn identically, and the surrounding words settle it.

05

Where a naive decoder breaks

Blocks 2 and 4 refuse to decode, and both failures share one cause: the top-segment row of the published art is not aligned with the glyphs beneath it. The two lower rows are pixel-accurate; the top row has drifted by one to two columns.

Block 2 — a top bar on the wrong glyph

Underscores sit at columns 5, 13, 17, 21, while the cells start at 4, 8, 12, 16, 20, 25, 27. Read literally, glyph 3 gains a bar it should not have (4 → 9) and glyph 7 loses the one it should have (c → l):

c l 9 s s 1 l   →   "clgssil"   not a word

Block 4 — a stray underscore welds two glyphs together

The last underscore sits at column 33, two columns left of where it belongs. It bridges the gap between the 1 at column 32 and the n at column 34, so a decoder that segments on runs of inked columns reads a single merged glyph and swaps the pair:

u n c 3 r t 4 n 1   →   "uncertani"   not a word

Both are recoverable — but not by trusting pixel positions.

06

Two constraints that resolve it

Stop treating the top row as positional evidence and start treating it as a count.

  • The underscore count is drift-independent. However far an underscore has slid sideways, it is still on the row. Block 2's top row holds exactly four, so exactly four of its seven glyphs carry a top segment. Block 4 holds seven — noting that t contributes two, being drawn _|_.
  • Only three glyph pairs are ambiguous (step 02), so the search space is a handful of candidates, not a brute force.

For block 2, the lower rows already fix glyphs 4, 5 and 6 as s, s, 1 — contributing two top segments — which leaves glyphs 1, 2, 3 and 7 free:

07

Automate it

The solver implements exactly the above against the unmodified art, in three stages:

  • tile() exhaustively tiles the two reliable rows with glyph cells, keeping only tilings that consume every inked column. Cells are allowed to overlap on blank columns, so a one-column 1 followed by a c needs no pitch assumption.
  • Each glyph may then swap with its top-segment twin, and candidates survive only if their total top-segment count matches the underscores in the top row.
  • Survivors are de-leeted and checked against /usr/share/dict/words.
$ python3 solve.py
  [1]  f4r3w3ll    farewell
  [2]  cl4ss1c     classic
  [3]  h3ll0       hello
  [4]  unc3rt41n   uncertain
  [5]  3r4!        era

  ASIS{f4r3w3ll_cl4ss1c_h3ll0_unc3rt41n_3r4!}

Every block yields exactly one reading, and the script aborts if any block is ambiguous — so the output is a proof rather than a preference.

—

Takeaways

  • Three-row ASCII art is almost always a seven-segment display. Build the font from the art rather than importing one; authors add glyphs no real display can render.
  • Segment on the rows you trust. The lower two rows carry the verticals and are self-aligning. The top row is one sparse character per glyph — exactly where whitespace damage hides, in the original art or in the paste.
  • When position is unreliable, count instead. The number of top segments survives any horizontal drift, and it closed both ambiguities here.
  • Let the plaintext arbitrate. With a leet mapping and a wordlist, a warm-up encoding collapses to a single reading. If a decode is not a word, the decode is wrong — not the wordlist.
